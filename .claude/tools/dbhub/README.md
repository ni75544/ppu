# Project-local DBHub runtime (connection-pool cap patch)

Task 24B prerequisite. This directory holds a **project-local, version-pinned**
copy of the `@bytebase/dbhub` MCP server plus a reproducible patch that caps its
MariaDB connection pool. It exists to stop the DBHub connector from saturating
the QA MariaDB `max_connections` (the pool defaulted to ~10 eager connections
per instance; ~10 instances filled all 100 slots and blocked every Drupal CLI
bootstrap with `[1040] Too many connections`).

The global npm installation is **not** modified. The MCP launcher
(`.claude/scripts/dbhub-mcp.cjs`) resolves this local runtime and refuses to
start unless the patch is present.

## What the patch does

`@bytebase/dbhub` 1.2.3 builds a `connectionConfig` with no pool-size key and
calls `mariadb.createPool(connectionConfig)` once, so the driver defaults apply:
`connectionLimit=10`, `minimumIdle=connectionLimit` (eager prewarm),
`idleTimeout=1800s`. The single call site in the connector chunk
(`node_modules/@bytebase/dbhub/dist/mariadb-<hash>.js`) is changed to:

```js
this.pool = mariadb.createPool({ ...connectionConfig, connectionLimit: 2, minimumIdle: 0, idleTimeout: 60 });
```

- `connectionLimit: 2` — caps **this pool** at two connections. This bounds each
  pool created at this call site. It is not by itself proof of one pool instance
  per process: a single `createPool()` call site does not establish that the
  connector is constructed exactly once per process — that is a separate runtime
  fact, not shown by the call-site count alone.
- `minimumIdle: 0` — disables the pool's eager idle prewarm, so the pool does not
  open connections merely to hold them idle (`Math.min(0, 2) = 0`). This is **not**
  proof that DBHub initialization or health checks open no connections: the
  connector still issues a `SELECT VERSION()` probe on connect, and any
  init/health path may open a connection on demand.
- `idleTimeout: 60` — sets the idle-release target to 60s. The driver documents
  `idleTimeout` in **seconds** and requires it below the server `wait_timeout`.
  MariaDB's *documented default* `wait_timeout` is 28800s, which 60 is below —
  but that documented default is not a current runtime measurement of this
  server. A configured 60s target is also not evidence that idle connections were
  actually released after 60s; that is runtime behaviour and is not verified here.

Everything else in `connectionConfig` (host, port, database, credentials,
`multipleStatements`, TLS/`ssl`, the read-only transaction path, and the finite
default `acquireTimeout=10000ms`) is preserved unchanged — the patch only spreads
the existing config and adds three pool options. **Preserve this patch; do not
introduce additional pooling changes without a reproduced defect.**

## Provisioning (locked restore)

Restore the exact pinned tree from `package-lock.json` and reapply the patch:

```bash
rtk npm --prefix .claude/tools/dbhub ci
```

`npm ci` performs a **locked** install from `package-lock.json` (not a semver
range resolve) and runs `postinstall` (`node provision.cjs`), which reapplies the
patch on disk. This is the reproducible-on-this-workstation mechanism. The
applier is:

- **idempotent** — an already-patched connector is left untouched (exit 0);
- **version-checked** — refuses to patch unless `@bytebase/dbhub` is `1.2.3` and
  the resolved mariadb driver is the reviewed `3.5.4` (otherwise it fails with an
  instruction to revalidate pool-option behaviour and update the reviewed
  version in `patch-target.cjs`);
- **drift-safe** — fails explicitly if the connector contains neither the
  reviewed call nor the patched form, or if there is not exactly one call site.

Verify without writing:

```bash
rtk npm --prefix .claude/tools/dbhub run verify
```

## Reproducible on this workstation vs preserved in repository history

These are distinct guarantees and only the first currently holds:

- **Reproducible on this workstation** — `rtk npm --prefix .claude/tools/dbhub ci`
  regenerates the pinned dependency tree and reapplies the patch on disk from the
  local `package.json`/`package-lock.json`. This works today from the on-disk
  copies.
- **Preserved in repository history** — the six sources are now *eligible* for
  version control but are **untracked and not yet committed**. Until they are
  committed, they are not in history and a fresh clone would not carry them;
  reproducibility would then depend on these on-disk files still being present.

## Owner-operated reload (frees the saturated pool)

Provisioning patches the on-disk runtime only. Already-running DBHub instances
keep their loaded code and their existing pools, so capacity is not freed until
each client reloads its DBHub MCP server. The smallest owner-operated procedure:

1. In each client that has DBHub enabled (the Codex CLI sessions hold the
   majority and oldest connections, plus any Claude sessions), **disable then
   re-enable the `dbhub` MCP server** via that client's own MCP control — or
   close the surplus sessions. Each reload drains that child's `dbhub_ro`
   connections and the replacement opens the capped (≤2, lazy) pool.
2. No process kills, SQL session kills, container restarts, or global client
   configuration changes are required or intended.

Only after capacity is freed should read-only runtime verification be run
(loaded runtime path, live connection usage, idle release, QA Drupal bootstrap).
Runtime success must not be claimed from configuration inspection alone.
